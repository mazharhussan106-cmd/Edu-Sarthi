term: docker run
cue: Which command creates a new container from an image and starts it?
kind: CLI command
frequency: Very high
importance: 5
origin: An image does nothing until it is started, so one command was needed to create and start a container in a single step.
pro_tip: Add --rm for throwaway containers so they clean themselves up when they stop.
memory_story: Pressing run is pressing the power button on a sealed box you just unpacked.
visual: An image turning into a running container with a name and a port.
emotion: The thrill of seeing your first service answer in seconds.
meaning: docker run creates a container from an image, starts it, and optionally attaches your terminal to it.
code: docker run -d --name web -p 8080:80 nginx:1.27
output: A long container ID is printed, and nginx is now reachable at http://localhost:8080.
explanation: -d runs the container in the background. --name gives a readable name instead of a random one. -p publishes a container port on the host. Everything after the image name is the command and its arguments. If the image is missing locally, Docker pulls it first.
simple_explain: docker run = create + start. Use -d for background, --name for a label, -p for ports.
analogy: It is like unpacking a boxed appliance and plugging it in at once.
syntax: docker run [options] image [command] [args]
anatomy: -d = background | --name = label | -p host:container = publish port | --rm = remove on exit | -it = interactive terminal
example_1: docker run --rm hello-world
example_2: docker run -it --rm alpine sh
example_3: docker run -d -e POSTGRES_PASSWORD=secret postgres:16
variation: docker run --restart unless-stopped -d myapp   // restart after crashes and reboots
used_with: docker ps, docker logs, docker stop
related: docker ps, docker exec, port mapping
alternatives: docker compose up | docker create followed by docker start
where_used: Local testing | Quick tools | One-off jobs
mini_conversation: A: The page does not load. | B: You forgot -p, so no host port points at the container.
misconception: ✗ Running docker run twice just restarts the same container → ✓ Each docker run creates a brand new container
confused_with: docker run vs docker start: run creates a new container, start restarts an existing one.
avoid: Do not use unnamed, never-removed containers for everyday testing.
wrong_code: docker run nginx -d
right_code: docker run -d nginx
memory_trick: Options go before the image, command after.
real_project: Starting a local Postgres container so the team could test migrations.
real_interview: An interviewer may ask: What does docker run do step by step?
real_daily: It is like unpacking an appliance and switching it on at once.

kind: CLI command

origin: Containers run in the background with no terminal, so Docker stores their output and lets you read it later with logs.
pro_tip: Use -f to follow new lines and --tail to avoid flooding your screen.
memory_story: Logs are the container's diary that you read when it misbehaves.
visual: Lines of text scrolling from a running service.
emotion: The satisfaction of spotting the real error line.
meaning: docker logs prints the standard output and standard error that a container has written.
code: docker logs -f --tail 100 --since 10m web

A service that writes only to a file inside the container shows nothing here. --since limits by time, and -t adds timestamps. Logs live as long as the container, so removing it removes them unless a log driver ships them elsewhere.
simple_explain: docker logs name shows output, -f follows it, --tail limits the lines.
analogy: It is like reading a diary the container wrote while you were away.
syntax: docker logs [-f] [--tail N] [--since time] [-t] container
anatomy: -f = follow | --tail N = last N lines | --since = recent only | -t = timestamps
example_1: docker logs web
example_2: docker logs --tail 50 web
example_3: docker logs -t --since 1h web
variation: docker compose logs -f api   // follow one Compose service
used_with: docker ps, docker exec, log drivers
related: docker ps, docker exec, logging and monitoring
alternatives: Central log tools | docker compose logs
where_used: Debugging | Checking startup | Incident response
mini_conversation: A: The container exits at once. | B: Check docker logs to read its last error.
misconception: ✗ docker logs shows every file inside the container → ✓ It shows only what the main process sent to stdout and stderr
confused_with: docker logs vs docker exec: logs reads past output, exec runs a new command.
avoid: Do not write application logs only to a file inside the container.
wrong_code: docker logs web --follow-all
right_code: docker logs -f web
memory_trick: Follow flag keeps the diary open.
real_project: Reading startup logs to find a missing environment variable in staging.
real_interview: An interviewer may ask: How do you debug a container that exits immediately?
real_daily: It is like reading the diary of someone who left the room.
mcq_question: What does docker logs read from?
mcq_options: A) The host system journal only B) The standard output and error of the main process C) The image layers D) Every file in the container
mcq_answer: B
mcq_why: Docker records the main process output streams.
fill_blank: The flag ____ keeps streaming new lines as they appear → -f

task_answer: docker logs --tail 20 api

kind: CLI command
frequency: Very high

origin: When a live container misbehaves you want to look inside it, so Docker lets you start a second process in its environment.
pro_tip: Use exec for inspecting, but fix the cause in the Dockerfile rather than patching a live container.
memory_story: Exec is a side door into a room where the main process keeps working.

meaning: docker exec runs a new command inside a running container, often an interactive shell.

analogy: It is like walking through a side door into a room that stays busy.
syntax: docker exec [-it] [-u user] [-w dir] container command

used_with: docker ps, docker logs, docker cp
related: docker run, docker logs, debugging a failing container
alternatives: docker run for a new container | docker compose exec
where_used: Debugging | Running migrations | Database access

avoid: Do not hot-fix production containers by hand through exec.
wrong_code: docker exec web sh
right_code: docker exec -it web sh
memory_trick: Interactive shell needs both i and t.
real_project: Opening a shell in the API container to check mounted config files.
real_interview: An interviewer may ask: How would you inspect a running container?
real_daily: It is like entering through a side door without stopping the work.

mcq_answer: C
mcq_why: -i keeps input open and -t allocates a terminal.

term: docker stop and docker rm
cue: Which commands stop a container and then delete it?
kind: CLI command
frequency: Very high
importance: 4
origin: Containers pile up as you test, so Docker separates stopping a process from deleting its leftover container.
pro_tip: docker rm -f stops and removes in one step when you are sure.
memory_story: Stop turns off the machine, and rm carries the machine away.
visual: A container going from Up to Exited to gone.
emotion: The tidy feeling of an empty container list.
meaning: docker stop sends a polite stop signal and then kills after a timeout, and docker rm deletes a stopped container.
code: docker stop web¶docker rm web¶docker rm -f old-api
output: The names are echoed back, web is gone, and old-api is force removed even if it was running.
explanation: stop sends SIGTERM and waits, 10 seconds by default, before SIGKILL. A stopped container still exists and keeps its writable layer until it is removed. rm refuses to delete a running container unless you add -f. Named volumes always survive rm, and -v removes only anonymous volumes.
simple_explain: stop shuts it down gracefully, rm deletes it, rm -f does both quickly.
analogy: It is like powering a machine off and then carrying it out of the room.
syntax: docker stop [-t seconds] container | docker rm [-f] [-v] container
anatomy: stop = graceful shutdown | -t = wait time | rm = delete | -f = force | -v = remove anonymous volumes
example_1: docker stop web
example_2: docker rm -f web
example_3: docker rm $(docker ps -aq --filter status=exited)
variation: docker container prune   // remove all stopped containers
used_with: docker ps, docker run, docker volume
related: docker ps, volumes, docker prune
alternatives: docker run --rm | docker compose down
where_used: Cleanup | Redeploys | Local development
mini_conversation: A: The name is already in use. | B: Remove the old container with docker rm first.
misconception: ✗ docker stop deletes the container → ✓ It only stops it, and the container remains until removed
confused_with: docker stop vs docker kill: stop is graceful, kill is immediate.
avoid: Do not remove a database container without checking where its data lives.
wrong_code: docker rm web
right_code: docker stop web && docker rm web
memory_trick: Stop first, then remove, or force it.
real_project: Cleaning exited test containers before each local integration run.
real_interview: An interviewer may ask: What signal does docker stop send?
real_daily: It is like switching a machine off before carrying it out.
mcq_question: What does docker rm refuse to do by default?
mcq_options: A) Delete a named image B) Print its name C) Delete a running container D) Delete a stopped container
mcq_answer: C
mcq_why: A running container must be stopped or forced with -f.
fill_blank: docker stop first sends the signal ____ before force killing → SIGTERM
hindi_to_task: Force remove the container called old-api.
task_answer: docker rm -f old-api
own_task: Remove every exited container with one command.
practice_question: Does removing a container delete its named volumes?
practice_answer: No, named volumes survive unless you delete them explicitly.

cue: Which commands turn a Dockerfile into an image and give that image a name?
kind: CLI command
frequency: Very high
importance: 5
origin: A Dockerfile is only instructions, so Docker needs a command that executes them and stores the result as an image.
pro_tip: Always pass a name with -t, and build from the folder that holds your source.
memory_story: Build is the oven that bakes the recipe, and tag is the label on the box.
visual: Steps scrolling by and an image appearing in the list.
emotion: The pleasure of a build finishing without errors.
meaning: docker build reads a Dockerfile and a build context to create an image, and docker tag adds another name to an existing image.
code: docker build -t myapp:1.0 -f Dockerfile .¶docker tag myapp:1.0 myapp:latest
output: Each step runs, the image myapp:1.0 is created, and a second tag latest points at the same image.
explanation: The final dot is the build context, the folder sent to Docker, and COPY can only use files inside it. -f picks a Dockerfile with another name. --build-arg passes ARG values and --no-cache ignores the cache. Tagging does not copy data, it adds a name to the same image ID.
simple_explain: docker build -t name . builds an image from the Dockerfile in this folder.
analogy: It is like baking from a recipe and then sticking labels on the box.
syntax: docker build [-t name:tag] [-f file] [--build-arg K=V] context
anatomy: -t = name and tag | -f = Dockerfile path | context = folder sent to Docker | --no-cache = rebuild all
example_1: docker build -t api:dev .
example_2: docker build --build-arg NODE_VERSION=22 -t web .
example_3: docker build --no-cache -t api:clean .
variation: docker buildx build --platform linux/amd64 -t api .   // build for a chosen CPU
used_with: Dockerfile, .dockerignore, registries
related: layers and cache, .dockerignore, BuildKit
alternatives: docker compose build | CI build actions
