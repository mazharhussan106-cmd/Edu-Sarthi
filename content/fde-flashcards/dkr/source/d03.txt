kind: Storage concept

output: The volume is created, mounted in the database folder, and listed after the container is removed too.

simple_explain: Mount a named volume at the folder where an app saves data, and the data outlives the container.
analogy: It is like a safe deposit box that stays when the clerk changes.

kind: Storage concept

code: docker run --rm -v "$(pwd)":/app -w /app node:22 node index.js

simple_explain: A bind mount shares one real host folder with the container. Great for development.
analogy: It is like a window that shows your own desk inside another room.
syntax: docker run -v /host/path:/container/path[:ro] image
anatomy: /host/path = real folder | /container/path = where it appears | :ro = read only
example_1: docker run -v "$(pwd)":/site -p 8080:80 nginx
example_2: docker run -v "$(pwd)"/conf:/etc/app:ro myapp
example_3: docker run --mount type=bind,src="$(pwd)",dst=/app myapp
variation: volumes: ["./src:/app/src"]   // relative paths work in Compose files
used_with: docker run, Compose, hot reload tools
related: volumes, tmpfs, docker run
alternatives: Named volumes | docker cp for one-off copies
where_used: Local development | Config files | Live reload

confused_with: Bind mount vs volume: bind uses your path, volume uses Docker's storage.
avoid: Do not bind mount sensitive host folders read-write.
wrong_code: docker run -v app:/app myapp
right_code: docker run -v "$(pwd)":/app myapp
memory_trick: A slash path means a real host folder.
real_project: Mounting source code so the dev server reloaded on every save.
real_interview: An interviewer may ask: When would you choose a bind mount?
real_daily: It is like a window showing your own desk elsewhere.
