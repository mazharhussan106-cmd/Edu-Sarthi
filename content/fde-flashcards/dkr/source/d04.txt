cue: How do you declare shared storage and private networks in a Compose file?
kind: Compose concept
frequency: High
importance: 4
origin: Real stacks need persistent data and separated traffic, so Compose has top-level sections for volumes and networks.
pro_tip: Put the database on a private network that the public proxy cannot reach.
memory_story: Top-level sections are the shared rooms that every service can be given keys to.
visual: Services attached to named networks and storage.
emotion: The tidy feeling of clear boundaries.
meaning: Top-level volumes and networks sections declare named resources that services then attach to by name.
code: services:¶  db:¶    image: postgres:16¶    environment:¶      POSTGRES_PASSWORD: example¶    volumes:¶      - pgdata:/var/lib/postgresql/data¶    networks: [backend]¶volumes:¶  pgdata:¶networks:¶  backend:
output: Compose creates the pgdata volume and the backend network, and attaches db to both.
explanation: Without a networks section Compose makes one default network. Declaring several lets you separate public and private traffic. A volume named at the top level survives down unless you remove it. A bind mount is written as a path directly under a service.
simple_explain: Declare volumes and networks at the bottom, then list them under each service.
analogy: It is like shared rooms that services receive keys to.
syntax: services: name: volumes: [vol:/path] networks: [net] then top-level volumes: and networks:
anatomy: volumes = storage | networks = private links | service lists = which ones it uses
example_1: volumes: [./src:/app/src]
example_2: networks: [frontend, backend]
example_3: external: true   // reuse a volume created outside
variation: networks: backend: internal: true   // no outside access
used_with: depends_on, bridge networks, volumes
related: volumes, bridge networks, depends_on and health checks
alternatives: Default network only
where_used: Databases | Multi-tier apps | Isolation
mini_conversation: A: Can the proxy reach the database? | B: Not if they share no network.
misconception: ✗ Every service in a Compose file needs its own network → ✓ All services share a default network unless you declare more
confused_with: Service volume list vs top-level volumes: one attaches, the other declares.
avoid: Do not forget to declare a named volume at the top level.
wrong_code: services:¶  db:¶    volumes: [pgdata:/data]
right_code: services:¶  db:¶    volumes: [pgdata:/data]¶volumes:¶  pgdata:
memory_trick: Declare at the bottom, use at the top.
real_project: Isolating the database on an internal network behind the API.
real_interview: An interviewer may ask: How do you keep a database private in Compose?
real_daily: It is like giving keys only to the services that need a room.
mcq_question: Where is a named volume declared in Compose?
mcq_options: A) In .dockerignore B) Inside the Dockerfile C) In the top-level volumes section D) In the image tag
mcq_answer: C
mcq_why: Named volumes need a top-level declaration.
fill_blank: A network that blocks outside access is marked ____ → internal

cue: How do you make one service wait until another is truly ready?
kind: Compose concept
frequency: High

origin: A started container is not always a ready one, so Compose can wait for a health check rather than just a start.
pro_tip: Pair condition service_healthy with a real health check, never rely on start order alone.
memory_story: Depends_on is a waiter who holds the dish until the kitchen says it is ready.
visual: An arrow from web to db with a green check.
emotion: The relief of no more random start-up crashes.
meaning: depends_on sets start order, and with condition service_healthy it waits until the dependency passes its health check.
code: services:¶  db:¶    image: postgres:16¶    environment:¶      POSTGRES_PASSWORD: example¶    healthcheck:¶      test: ["CMD-SHELL", "pg_isready -U postgres"]¶      interval: 5s¶      retries: 10¶  api:¶    build: .¶    depends_on:¶      db:¶        condition: service_healthy
output: The api container starts only after pg_isready reports that the database accepts connections.
explanation: Plain depends_on only waits for the container to start, which may be long before the database is ready. A healthcheck defines a command that Docker runs repeatedly. Only when it succeeds is the service marked healthy. Your app should still retry connections, because a database can restart later.
simple_explain: Add a healthcheck to the dependency, then wait for service_healthy.
analogy: It is like a waiter holding a dish until the kitchen says it is ready.
syntax: depends_on: service: condition: service_healthy
anatomy: depends_on = order | condition = what to wait for | healthcheck = readiness test
example_1: condition: service_started
example_2: condition: service_completed_successfully
example_3: healthcheck: test: ["CMD", "curl", "-f", "http://localhost/health"]
variation: start_period: 30s   // grace time before failures count
used_with: healthchecks, restart policies, migrations
related: HEALTHCHECK, Compose commands, debugging a failing container
alternatives: Retry logic in the app | Wait scripts

memory_trick: Started is not the same as ready.

term: Environment and env files
cue: How do you pass settings and secrets into Compose services without hard-coding them?
kind: Compose concept
frequency: Very high
importance: 5
origin: Settings change per environment, so Compose reads variables from the shell and from env files rather than from the YAML itself.
pro_tip: Commit a .env.example, never the real .env file.
memory_story: An env file is a sealed envelope of settings handed to each container at start.
visual: A .env file feeding values into a service.
emotion: The calm of keeping passwords out of the repository.
meaning: Compose passes variables to containers through environment and env_file, and substitutes ${VAR} values in the YAML from the shell or a .env file.
code: services:¶  api:¶    image: myapi:1.0¶    env_file: [.env.api]¶    environment:¶      LOG_LEVEL: ${LOG_LEVEL:-info}
output: Variables from .env.api are loaded, and LOG_LEVEL falls back to info if it is not set.
explanation: A file named .env next to the compose file is used for substitution in the YAML. env_file loads variables into the container itself. The syntax ${VAR:-default} supplies a default, and ${VAR:?error} fails if it is missing. Values in environment override those from env_file.
simple_explain: Keep settings in an env file, reference them with ${NAME}, and ignore the file in Git.
analogy: It is like a sealed envelope of settings given to each container.
syntax: env_file: [file] | environment: KEY: value | ${VAR:-default}
anatomy: env_file = load file | environment = inline | ${VAR:-x} = default value
example_1: DATABASE_URL=postgres://db:5432/app
example_2: ${PORT:-8000}
example_3: ${API_KEY:?API_KEY is required}
variation: docker compose --env-file prod.env up   // choose another env file
used_with: .gitignore, secrets, CI variables
related: ENV and ARG, secrets, override files
alternatives: Docker secrets | Secret managers
where_used: Configuration | Database URLs | Per-environment settings
mini_conversation: A: Where do I put the database password? | B: In an ignored env file, not the YAML.
misconception: ✗ An env file is secure storage → ✓ It is plain text, so keep it out of Git and image layers
confused_with: .env substitution vs env_file: one fills the YAML, the other feeds the container.
avoid: Do not commit .env files with real secrets.
wrong_code: environment:¶  PASSWORD: hunter2
right_code: environment:¶  PASSWORD: ${DB_PASSWORD:?set DB_PASSWORD}
memory_trick: Commit the example, ignore the real one.
real_project: Using a committed .env.example so new developers knew every needed variable.
real_interview: An interviewer may ask: How do you keep secrets out of a Compose file?
real_daily: It is like handing each person a sealed envelope.

meaning: Compose merges multiple files in order, and settings in later files override or extend those in earlier ones.

explanation: A file named compose.override.yaml is merged automatically with compose.yaml. Lists such as ports are combined, while single values like image are replaced. The config command shows the final result, which is the safest way to check what will run. Use it before deploying.
simple_explain: Put the common part in the base file and the differences in an override.
analogy: It is like laying a transparent sheet over a base drawing.
syntax: docker compose -f base.yaml -f override.yaml up
anatomy: -f = file | later file wins | config = show merged result
example_1: docker compose config
example_2: docker compose -f compose.yaml -f compose.test.yaml run tests
example_3: docker compose config --services
