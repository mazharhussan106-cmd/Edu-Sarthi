cue: How do you replay your branch's commits on top of another branch's latest work without creating a merge commit?
kind: Git command
frequency: High
importance: 4
origin: A merge adds a joining commit and can tangle the history of long-lived branches, so rebase rewrites your commits onto a new base to keep history in one straight line.
pro_tip: Rebase only a branch that is yours alone and has not been pushed.
memory_story: Rebase picks up your commits and sets them down again on fresh ground.
visual: Train carriages are lifted off one track and coupled to the front of another.
emotion: The satisfaction of a neat, straight history.
meaning: git rebase replays the commits of the current branch on top of another branch.

output: Successfully rebased and updated refs/heads/feature/login.
explanation: Rebase rebuilds each commit on the new base with a new hash. The history looks straight but the hashes change. Rebasing a pushed branch needs a force push, so do it only on private branches.
simple_explain: Rebase makes your feature branch look as if you had started your work after main's latest code. The history is clean, but your commits are rewritten.
analogy: It is like copying your own pages to the end of a newer book.
syntax: git rebase <base-branch>
anatomy: git rebase = command | <base-branch> = the branch to place your commits on
example_1: git rebase main
example_2: git rebase --continue
example_3: git rebase --onto main old-base feature
variation: git rebase --abort   # stop¶git pull --rebase   # pull with rebase
used_with: --continue, --abort, git pull --rebase
related: git merge, git rebase -i, git reflog
alternatives: git merge
word_family: git rebase, git merge, git cherry-pick, git reflog, git pull
where_used: Updating a feature branch from main | Keeping history clean | Before a PR
mini_conversation: A: My branch has fallen behind main. | B: Run git rebase main and your commits will sit on top of main.
misconception: ✗ Rebase and merge give the same result → ✓ Rebase straightens history but changes the commit hashes, while merge keeps the original commits
confused_with: rebase vs merge: merge joins histories, rebase rewrites commits on a new base.
avoid: Do not rebase a shared or already pushed branch.
wrong_code: git rebase feature main --push
right_code: git rebase main
memory_trick: Rebase means setting a new base.
real_project: Rebasing a feature branch onto the latest main before the PR so the history stays straight.

code: git blame -L 10,15 src/app.js
output: 8b7d1e2 (Asha 2026-09-12 10:03) function total(cart) {¶3f2a9c1 (Ravi 2026-08-30 17:21)   return sum(cart);
explanation: Each line shows the commit hash, author and date. -L picks a range of lines. Run git show on that hash to see the full commit and its message.
simple_explain: Blame lets you learn when and why a particular line was written. Then git show with that hash gives you the full reason.
analogy: It is like seeing the writer's name and date beside every sentence of a book.
syntax: git blame [-L <start>,<end>] <file>
anatomy: git blame = command | -L = range of lines | <file> = file name
example_1: git blame src/app.js
example_2: git blame -L 20,40 src/app.js
example_3: git blame -w -C src/app.js
variation: git blame -w   # ignore whitespace¶git blame -C   # detect copied lines
used_with: -L, -w, -C, git show
related: git log, git show, git bisect
alternatives: The Blame button on GitHub
word_family: git blame, git log, git show, git bisect, git diff
where_used: The reason for an old line | Source of a bug | Understanding code
mini_conversation: A: Why was this odd line written? | B: Run git blame to find the commit and read its message.
misconception: ✗ git blame tells you whose fault the mistake is → ✓ Blame only shows who wrote a line and when, and the commit message is where you learn the reason
confused_with: git blame vs git log: blame shows the last commit for each line, log shows the whole commit history.
avoid: Do not use blame as a tool to blame people.
