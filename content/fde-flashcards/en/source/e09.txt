kind: Git command

simple_explain: Pick a commit from the log and read its whole story with show: who wrote it, why, and what changed.
analogy: It is like opening one envelope and reading the letter and every page with it.

example_2: git show HEAD~2 --stat

related: git log, git diff, git blame
alternatives: The commit page on GitHub
word_family: git show, git log, git diff, git blame, git tag

cue: How do you tell Git that you removed or renamed a tracked file?
kind: Git command
frequency: Medium
importance: 4
origin: Removing a file by hand made you tell Git separately, so rm and mv do the job and stage it straight away.
pro_tip: Use git rm --cached when you want Git to stop tracking a file but keep it on disk.
memory_story: rm takes out the rubbish and notes it in the ledger, and mv renames and corrects the entry.
visual: One file gets a new name tag and another goes into a bin, both stamped by Git.
emotion: The comfort that history stays tidy while you clean up.

code: git rm old.txt¶git mv draft.md notes.md¶git status -s
output: D  old.txt¶R  draft.md -> notes.md
explanation: git rm deletes the file from the folder and stages the removal. --cached removes it only from Git and leaves the file on disk. git mv renames the file and Git shows it as a rename, which makes history easier to follow.
simple_explain: Use git rm instead of deleting by hand and Git knows at once. Use git mv to rename so history stays clean.
analogy: It is like removing an entry from the ledger or correcting a name, and noting that down too.
syntax: git rm [--cached] <file>  |  git mv <old> <new>
anatomy: git rm = remove | --cached = only from Git | git mv = rename or move
example_1: git rm old.txt
example_2: git rm --cached .env
example_3: git mv draft.md notes.md
variation: git rm -r build/   # a whole folder¶git rm -f file.txt   # even with changes
used_with: --cached, -r, git commit, .gitignore
related: .gitignore, git restore, git add
alternatives: Delete by hand and run git add -A
word_family: git rm, git mv, git add, git commit, git restore
where_used: Cleaning up | Removing a file committed by mistake | Renaming a file
mini_conversation: A: I committed .env, how do I ignore it now? | B: Run git rm --cached .env and add it to .gitignore.
misconception: ✗ git rm --cached also deletes the file from the folder → ✓ --cached only stops Git tracking it, and the file stays in the folder
confused_with: git rm vs git rm --cached: rm deletes the file, --cached only removes it from Git.
avoid: Do not use git rm -f carelessly on a file with changes.
wrong_code: git rm --untrack .env
right_code: git rm --cached .env
memory_trick: With --cached, stop tracking but keep the file.
real_project: Taking a secrets file committed by mistake out of Git with git rm --cached and adding it to .gitignore.
real_interview: An interviewer may ask: How do you remove a file from Git without deleting it?

mcq_why: --cached removes it only from Git's record, not the file.

output: Tracking "*.psd"
explanation: The tracking rule is written into .gitattributes, so that file must be committed too. On push the real file goes to the LFS server. GitHub has limits and quotas for LFS, so check your plan.
simple_explain: Putting big files straight into Git makes the repo heavy. LFS keeps the real file elsewhere and a pointer in the repo, so cloning stays fast.
analogy: It is like heavy goods in a warehouse and only a slip at home.

variation: git lfs untrack "*.psd"   # stop tracking¶git lfs pull   # fetch the real files
used_with: .gitattributes, git add, git push
related: .gitattributes, clone, repository size
alternatives: Keeping large files outside the repo in cloud storage
word_family: LFS, pointer, .gitattributes, binary, track
where_used: Game assets | Design files | Machine learning models

avoid: Do not expect a file already committed to shrink the history just because you write an LFS rule.
wrong_code: git lfs add "*.psd"
right_code: git lfs track "*.psd"
memory_trick: LFS is a Large File's safe slip.
real_project: Tracking a game's large texture files with LFS.
real_interview: An interviewer may ask: How does LFS work?
real_daily: It is like heavy goods in a warehouse and only a slip at home.

kind: Git command

simple_explain: A submodule pins another repo at a fixed version. The parent only remembers which commit it wants, and an update happens when you commit a new pointer.
analogy: It is like a note in a book saying to read only that edition of another book.

example_1: git submodule add https://github.com/asha/ui-kit.git libs/ui-kit
example_2: git clone --recurse-submodules https://github.com/asha/app.git
example_3: git submodule update --init --recursive
variation: git submodule update --remote   # fetch the newer version¶git submodule status
used_with: --recurse-submodules, update, .gitmodules
related: git clone, git subtree, package managers
alternatives: git subtree, or a package manager (npm, pip)
word_family: submodule, .gitmodules, pointer, recurse, pin
where_used: Shared libraries | Large multi-repo projects | Pinning third-party code

misconception: ✗ A submodule always stays on its latest version → ✓ A submodule is pinned to one commit, and you must update the pointer by hand to get a newer version
confused_with: submodule vs package manager: a submodule pins a git commit, a package manager handles versions and dependencies.
avoid: Do not forget to commit the new pointer in the parent after changing a submodule.
wrong_code: git submodule clone https://github.com/asha/ui-kit.git
right_code: git submodule add https://github.com/asha/ui-kit.git libs/ui-kit
memory_trick: Submodule means a sub-repo pinned to one commit.
real_project: Sharing one UI library across two apps at the same version through a submodule.
real_interview: An interviewer may ask: When would you use a submodule and when not?
real_daily: It is like a note in a book to read only that edition of the other book.
