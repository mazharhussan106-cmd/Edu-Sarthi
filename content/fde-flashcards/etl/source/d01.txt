topic: 01 Ideas
level: Beginner
term: ETL vs ELT
cue: Which two patterns differ in whether data is reshaped before or after it reaches the warehouse?
category: Core concept
frequency: Very high
importance: 5
origin: Early warehouses had little computing power, so data was cleaned first, but cheap cloud warehouses made it practical to load first and transform later.
pro_tip: Say where the transformation runs, because that is the real difference.
memory_story: ETL is cooking in the kitchen before serving, and ELT is bringing raw groceries to the table and cooking there.
visual: Two arrows, one transforming before the warehouse and one transforming inside it.
emotion: The clarity of seeing why modern teams load raw data first.
definition: ETL extracts data, transforms it in a separate system, and then loads the result, while ELT extracts and loads raw data first and transforms it inside the warehouse.
explanation: In ETL a processing server or tool cleans and reshapes data before loading, which suits strict targets and sensitive data. In ELT the warehouse does the heavy work using SQL, which scales well and keeps raw data for replays. Many teams use ELT with tools such as dbt, but still apply light cleaning on the way in. The choice depends on volume, cost, privacy rules and team skills.
simple_explain: ETL transforms before loading, ELT loads first and transforms inside the warehouse.
analogy: ETL is cooking in the kitchen before serving, and ELT is bringing raw groceries to the table and cooking there.
formula_rule: ETL = transform, then load. ELT = load, then transform.
example_1: A script cleaning a CSV and then inserting it into a database.
example_2: Raw API data landed in a warehouse table and reshaped with SQL models.
example_3: Masking personal data before loading because the target must never hold it.
related: warehouse vs lake, batch vs streaming, dbt basics, data contracts
word_family: extract, transform, load, staging, raw layer
where_used: Data platforms | Analytics projects | Customer integrations
mini_conversation: A: Do we clean the data before it lands in the warehouse? | B: With ELT we load raw first and clean it there with SQL.
misconception: ✗ ELT means no transformation is needed → ✓ It only moves the transformation into the warehouse
contrast: ETL vs ELT: ETL transforms outside the target before loading, ELT transforms inside the target after loading.
avoid: Do not load sensitive fields raw if the target must never hold them.
memory_trick: ETL cooks first, ELT cooks last.
real_project: Moving a customer pipeline from ETL to ELT cut nightly run time by loading raw data once.
real_interview: An interviewer may ask: When would you choose ETL over ELT?
real_daily: It is like cooking in a kitchen versus cooking at the table.
mcq_question: Where does the transformation happen in ELT?
mcq_options: A) Nowhere B) Only in the browser C) On a separate server before loading D) Inside the warehouse
mcq_answer: D
mcq_why: ELT loads raw data and transforms it in the target.
fill_blank: In ETL the letter T stands for ____ → transform

cue: Which two extraction styles differ in whether you copy everything or only what changed?
kind: Extraction method
frequency: Very high
importance: 5
origin: Copying whole tables every night wastes time and money, so pipelines learned to move only new or changed rows.
pro_tip: Keep a watermark of the last successful value and only advance it after the load succeeds.
memory_story: Full load is photocopying the whole book, and incremental is copying only the new pages.
visual: A marker on a timeline showing what has been copied.
emotion: The relief of a fast nightly run.
meaning: A full load copies the entire source each run, while an incremental load copies only rows newer than a stored watermark such as a timestamp or id.
code: -- state table holds the watermark¶SELECT last_value FROM etl_state WHERE name = 'orders';¶SELECT * FROM orders WHERE updated_at > :last_value ORDER BY updated_at;¶-- after a successful load¶UPDATE etl_state SET last_value = :max_updated_at WHERE name = 'orders';
output: Only rows changed since the last run are read, and the watermark moves forward after success.
explanation: Incremental loads need a reliable change column, such as an updated timestamp or a rising id. Deletes are not visible with a simple watermark, so they need a soft delete flag or change data capture. Clock differences and late edits can be handled by re-reading a small overlap window. Full loads are simpler and fine for small tables.
simple_explain: Store a watermark, read only newer rows, and move the watermark after success.
analogy: Full load is photocopying the whole book, and incremental is copying only the new pages.
syntax: WHERE updated_at > :watermark

example_1: SELECT * FROM events WHERE id > 98200;
example_2: WHERE updated_at > :last - INTERVAL '10 minutes'
example_3: TRUNCATE staging; INSERT ... SELECT * FROM source;
variation: SELECT * FROM orders WHERE is_deleted = true AND updated_at > :last;   // catch soft deletes
used_with: watermarks, upserts, change data capture
