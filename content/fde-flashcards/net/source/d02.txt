topic: 03 Protocols
level: Beginner
term: TCP vs UDP
cue: Which two transport protocols differ in reliability versus speed?
category: Core concept
frequency: Very high
importance: 5
origin: Some applications need every byte in order, and others need speed above all, so two transport protocols were defined.
pro_tip: Choose TCP when correctness matters and UDP when late data is useless.
memory_story: TCP is registered post with receipts, and UDP is a postcard dropped in the box.
visual: One arrow with acknowledgements and another arrow with none.
emotion: The clarity of knowing why video calls and downloads behave differently.
definition: TCP is a connection-oriented protocol that delivers data reliably and in order, and UDP is a connectionless protocol that sends datagrams quickly with no guarantee.
explanation: TCP sets up a connection, numbers bytes, acknowledges them, retransmits losses and controls congestion. UDP has no setup and no retransmission, which means low delay. Web pages, email and databases use TCP. DNS queries, streaming, voice calls and games often use UDP. HTTP/3 builds reliability on top of UDP through QUIC.
simple_explain: TCP is safe and ordered, UDP is fast and light.
analogy: TCP is registered post with receipts, and UDP is a postcard dropped in the box.
formula_rule: TCP = reliable and ordered. UDP = fast and best effort.
example_1: A file download over TCP.
example_2: A voice call over UDP, where a late packet is useless.
example_3: A DNS query over UDP.
related: TCP handshake, ports, DNS, HTTP/3
word_family: TCP, UDP, datagram, reliable, connectionless
where_used: Application design | Troubleshooting | Firewalls
mini_conversation: A: Why does the video call skip instead of freezing? | B: It uses UDP, so lost data is skipped.
misconception: ✗ UDP is always worse than TCP → ✓ UDP is the right choice when speed matters more than perfect delivery
contrast: TCP vs UDP: TCP guarantees delivery, UDP does not.
avoid: Do not build your own reliability unless you must.
memory_trick: TCP checks every parcel, UDP just throws.
real_project: Explaining that a real-time feed used UDP and tolerated small losses by design.
real_interview: An interviewer may ask: When would you choose UDP over TCP?
real_daily: It is like registered post versus a postcard.

mcq_options: A) UDP B) TCP C) Both equally D) Neither
mcq_answer: B
mcq_why: TCP tracks and resends missing data.
fill_blank: A protocol with no setup step is called ____ → connectionless
apply: A live game needs the lowest delay and tolerates loss. Which protocol? → UDP

term: The TCP handshake
cue: Which three steps open a reliable TCP connection?
category: Core concept
frequency: High
importance: 4
origin: Both sides need to agree on starting numbers before reliable transfer, so a short exchange opens each connection.
pro_tip: A hanging connect usually means the SYN got no reply, which points to a firewall or a down host.
memory_story: It is a polite phone call that starts with hello, yes hello, and okay then.
visual: Three arrows between client and server labelled SYN, SYN-ACK and ACK.
emotion: The satisfaction of reading a capture and seeing it work.
definition: The TCP handshake is a three-step exchange of SYN, SYN-ACK and ACK segments that opens a connection and agrees on sequence numbers.
explanation: The client sends SYN, the server answers SYN-ACK, and the client confirms with ACK, after which data flows. A closed port answers with a reset, which gives connection refused. A filtered port gives no answer, so the client times out. Closing uses FIN segments. TLS adds its own handshake on top of TCP.
simple_explain: SYN, SYN-ACK, ACK, and then data can flow.
analogy: It is a polite phone call that starts with hello, yes hello, and okay then.
formula_rule: SYN → SYN-ACK → ACK.
example_1: A browser opening a connection to port 443.
example_2: A refused connection because the port is closed.
example_3: A timeout because a firewall dropped the SYN.
related: TCP vs UDP, TLS, firewalls, timeouts vs refused
word_family: SYN, ACK, handshake, reset, FIN
where_used: Packet captures | Troubleshooting | Security
mini_conversation: A: The connection times out. | B: The SYN may be dropped by a firewall.
misconception: ✗ Connection refused and timeout mean the same thing → ✓ Refused means someone answered no, and timeout means nobody answered
contrast: Reset vs timeout: a reset is an active refusal, a timeout is silence.
avoid: Do not assume a firewall when you see a reset.
memory_trick: SYN, SYN-ACK, ACK opens the call.
real_project: Using a capture to prove the server never sent SYN-ACK because a firewall dropped the request.
real_interview: An interviewer may ask: What are the three steps of the TCP handshake?

mcq_why: SYN opens the handshake.
fill_blank: The reply to a SYN is a ____ → SYN-ACK
apply: A client times out with no reply at all. What likely happens to the SYN? → It is dropped

category: Core concept

explanation: HTTP/2 removes the need for many parallel connections and compresses headers. A single lost packet can still stall all streams on TCP. HTTP/3 uses QUIC to avoid that, and speeds up connection setup. Both require TLS in practice. Support depends on the server, client and network, since some firewalls block UDP.
simple_explain: Newer versions send many requests in parallel on one connection and are faster.
analogy: HTTP/2 is one motorway with many lanes, and HTTP/3 builds it on a faster road base.
formula_rule: One connection, many streams, less waiting.

misconception: ✗ HTTP/2 and HTTP/3 change how you write API requests → ✓ Methods and status codes stay the same, only the transport improves
