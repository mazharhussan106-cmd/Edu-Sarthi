topic: 01 Basics
level: Beginner
term: Supabase
cue: Which open-source platform gives you a PostgreSQL database, login, file storage and a ready-made API in one project?
category: Backend platform
frequency: Very high
importance: 5
origin: Building a backend means setting up a database, authentication and storage separately, so Supabase packaged these around PostgreSQL as an open-source alternative to Firebase.
pro_tip: Think of it as a Postgres database with extra services wrapped around it, since that makes every part easier to understand.
memory_story: Supabase is a ready-furnished flat where the kitchen, lock and storeroom are already fitted, and you just move in.
visual: One project box containing a database, a login lock, a file cabinet and a live-updates signal.
emotion: The excitement of launching a full backend in an afternoon.
definition: Supabase is an open-source backend platform built on PostgreSQL that provides a database, authentication, storage, realtime updates, functions and automatic APIs.
explanation: When you create a project you get a real Postgres database. Supabase adds an auto-generated REST API over your tables, an authentication service, file storage, realtime subscriptions, edge functions and a dashboard. Your app talks to all of it through client libraries such as supabase-js.
simple_explain: Supabase gives your app a database, user login, file storage and an API without you building a server first. You can still use plain SQL because it is real PostgreSQL underneath.
analogy: It is like a ready-furnished flat where the kitchen, lock and storeroom are already fitted.
formula_rule: Supabase = Postgres + Auth + Storage + Realtime + Functions + auto API
example_1: A to-do app that stores tasks in a Supabase table and lets users log in.
example_2: A photo app that keeps pictures in Supabase Storage.
example_3: A chat app that shows new messages live through Realtime.
related: PostgreSQL, Firebase, Row Level Security, supabase-js
word_family: backend-as-a-service, Postgres, Auth, Storage, Realtime
where_used: Web and mobile apps | Prototypes and startups | Education projects
mini_conversation: A: Do I need to build my own server for login and data? | B: Not necessarily, Supabase provides the database, login and API for you.
misconception: ✗ Supabase is a new kind of database that is not SQL → ✓ Supabase is built on PostgreSQL, so standard SQL works as it does anywhere
contrast: Supabase vs a plain database: a database stores data, Supabase adds login, storage, APIs and realtime around it.
avoid: Do not treat Supabase as magic, learn the Postgres underneath.
memory_trick: Supabase is Postgres plus the extras you need.
real_project: Using Supabase for the database, login and file storage of a learning app.
real_interview: An interviewer may ask: What is Supabase and how does it differ from Firebase?
real_daily: It is like moving into a flat that is already furnished.
mcq_question: Which database does Supabase use underneath?
mcq_options: A) Redis B) MongoDB C) MySQL D) PostgreSQL
mcq_answer: D
mcq_why: Supabase is built on PostgreSQL.
fill_blank: Supabase is an open-source alternative to ____ → Firebase

category: Comparison
frequency: High

origin: Firebase made backends easy but locked developers into a NoSQL model, so Supabase offered a similar developer experience built on open-source PostgreSQL.
pro_tip: Pick Supabase when your data is relational and you like SQL, and Firebase when a document model and its tools fit better.

emotion: The confidence of choosing a tool that matches your data.
definition: Supabase uses PostgreSQL relational tables, SQL and open-source components, while Firebase uses NoSQL document databases and Google's proprietary services.
explanation: Supabase offers joins, constraints, SQL and Row Level Security, and it can be self-hosted. Firebase offers Firestore and a Realtime Database with a very polished mobile toolkit and tight Google integration. Data portability is easier with Postgres because you can export it with standard tools.
simple_explain: If your data fits neatly in related tables, Supabase feels natural. Firebase is document-based, which suits different shapes of data.
analogy: Firebase is folders of documents, and Supabase is tables with relationships, like linked spreadsheets.
formula_rule: Supabase = SQL and tables. Firebase = documents and collections.

related: PostgreSQL, SQL, NoSQL, vendor lock-in
word_family: SQL, NoSQL, document, relational, open source
where_used: Choosing a backend | Migration planning | Architecture discussions

misconception: ✗ Supabase and Firebase are the same product with different names → ✓ They differ in database type, openness and how you query and secure data
contrast: Supabase vs Firebase: relational SQL on Postgres versus NoSQL documents on Google's platform.
avoid: Do not choose a tool only because it is popular, check your data shape first.

@SUP-005
topic: 01 Basics
level: Intermediate
term: anon key vs service role key
cue: Which key is safe to expose in a browser because Row Level Security limits it, and which one bypasses all rules?
category: Security concept
frequency: Very high
importance: 5
origin: A browser app must talk to the database directly, so Supabase gives it a limited key that the database rules control, and keeps a separate all-powerful key for trusted servers.
pro_tip: If a key can bypass RLS, treat it like a master password and never ship it to the browser.
memory_story: The anon key is a visitor badge that opens only the doors your rules allow, and the service role key is the master key of the building.
visual: A badge with limited doors beside a master key labelled server only.
emotion: The alarm of realising which key you pasted into front-end code.
definition: The anon (client) key identifies unauthenticated or logged-in app users and is subject to Row Level Security, while the service role (secret) key has full access and bypasses RLS.
explanation: With the anon key, requests run as the anon or authenticated database role, so policies decide what rows are visible. The service role key runs with a role that bypasses RLS, so it can read and write everything. It belongs only in trusted server code, such as edge functions or backend jobs. Naming is moving towards publishable and secret keys, but the roles are the same idea.
simple_explain: Use the anon key in the app, because RLS guards your data. Use the service role key only on your own server, because it ignores the rules.
analogy: The anon key is a visitor badge and the service role key is the master key of the building.
formula_rule: anon or publishable key = browser, controlled by RLS. service role or secret key = server only, bypasses RLS.
example_1: A browser app using the anon key to fetch a user's own tasks.
example_2: A scheduled job using the service role key to clean old rows.
example_3: A leaked service role key forcing an immediate rotation.
related: Row Level Security, environment variables, Auth, secrets
word_family: anon, authenticated, service_role, publishable, secret
where_used: Every Supabase app | Security reviews | Backend jobs
mini_conversation: A: Can I use the service role key in my React app? | B: No, anyone could read it and bypass all your security rules.
misconception: ✗ The service role key is fine in the browser because the site is private → ✓ Anything in front-end code can be read, so the service role key must never be there
contrast: anon vs service role: anon is limited by RLS, service role bypasses it.
avoid: Never put the service role key in front-end code or a public repository.
memory_trick: Anon for the app, service role for the server.
real_project: Keeping the service role key only in a server-side job and the anon key in the web app.
real_interview: An interviewer may ask: What is the difference between the anon key and the service role key?
real_daily: It is like a visitor badge versus the master key of a building.
mcq_question: Which key bypasses Row Level Security?
mcq_options: A) The anon key B) The service role key C) The project URL D) The region
mcq_answer: B
mcq_why: The service role key has full access and ignores RLS.
fill_blank: The key that is safe for browsers is the ____ key → anon
apply: A scheduled cleanup job needs full access. Which key should it use? → The service role key, only in server-side code
explain_task: Explain the two keys in three lines.
own_task: Write where each key would live in a web app and a backend job.

topic: 01 Basics
level: Beginner
term: Environment variables for Supabase
cue: Where should the project URL and keys live so they are not written directly in your source code?
kind: Configuration practice
frequency: Very high
importance: 5
origin: Keys written in code spread through repositories and logs, so apps read them from environment variables that differ for each environment.
pro_tip: Prefix variables that must reach the browser as your framework requires, and keep server-only ones unprefixed.
memory_story: Environment variables are labelled drawers outside the code, and the code only asks for the drawer's name.
visual: A .env file beside the code, with arrows from names in the code to values in the file.
emotion: The calm of knowing a key is not hidden inside the code by accident.
meaning: Environment variables store the URL and keys outside the code, and the app reads them at run time.
code: # .env.local (not committed)¶NEXT_PUBLIC_SUPABASE_URL=https://abcd1234.supabase.co¶NEXT_PUBLIC_SUPABASE_ANON_KEY=your-client-key¶SUPABASE_SERVICE_ROLE_KEY=your-server-only-key¶// code¶const url = process.env.NEXT_PUBLIC_SUPABASE_URL;
output: The app reads the URL from the environment, and the keys never appear in the committed code.
explanation: In Next.js, variables starting with NEXT_PUBLIC_ are sent to the browser, so only the URL and client key should have that prefix. The service role key has no prefix, so it stays on the server. Add the env file to .gitignore, and set the same variables in your hosting provider.
simple_explain: Put the URL and keys in an env file, ignore that file in git, and read them with process.env. Never prefix the service role key so it stays server-only.
analogy: It is like labelled drawers outside the code, and the code only asks for a drawer's name.
syntax: process.env.NAME
anatomy: NEXT_PUBLIC_ = sent to the browser | no prefix = server only | .env.local = local file ignored by git
example_1: const url = process.env.NEXT_PUBLIC_SUPABASE_URL;
example_2: const key = process.env.NEXT_PUBLIC_SUPABASE_ANON_KEY;
example_3: const admin = process.env.SUPABASE_SERVICE_ROLE_KEY;
variation: Vite uses the VITE_ prefix for variables sent to the browser¶Hosting dashboards let you add the same variables for production
used_with: .gitignore, createClient, deployment settings
related: Project URL and API keys, anon key vs service role key, secrets
alternatives: A secrets manager for larger teams
where_used: Every deployment | Local development | CI settings
mini_conversation: A: Should I paste the key into my code for now? | B: No, put it in an env file and read it with process.env.
misconception: ✗ Anything in an env file is hidden from users → ✓ Variables with a public prefix are sent to the browser, so only non-secret values should have it
confused_with: Public prefix vs server-only variable: the prefixed one reaches the browser, the other stays on the server.
avoid: Do not give the service role key a public prefix.
wrong_code: NEXT_PUBLIC_SUPABASE_SERVICE_ROLE_KEY=your-server-only-key
right_code: SUPABASE_SERVICE_ROLE_KEY=your-server-only-key
memory_trick: Public prefix means public to everyone.
real_project: Setting the same variable names in the local file and the hosting dashboard.
real_interview: An interviewer may ask: How do you keep Supabase keys out of source code?
real_daily: It is like labelled drawers outside the code.
mcq_question: Which variable must not have a public prefix?
mcq_options: A) The service role key B) The client key C) The project URL D) The region name
mcq_answer: A
mcq_why: A public prefix sends the value to the browser, which would leak the service role key.
fill_blank: Add the env file to ____ so it is not committed → .gitignore
hindi_to_task: Read the Supabase URL from the environment variable NEXT_PUBLIC_SUPABASE_URL.
task_answer: const url = process.env.NEXT_PUBLIC_SUPABASE_URL;
own_task: Create an env file for a project and list which variables are public and which are not.
practice_question: What does the NEXT_PUBLIC_ prefix do in Next.js?
practice_answer: It makes the variable available in browser code.
