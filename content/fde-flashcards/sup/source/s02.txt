cue: Which database object is a saved query that you can read from like a table?
kind: SQL concept
frequency: Medium
importance: 3
origin: Complex queries are used again and again, so databases let you save a query under a name and treat the result as a virtual table.
pro_tip: Create views with security_invoker on, so Row Level Security of the underlying tables still applies to the caller.
memory_story: A view is a window cut into your tables that always shows the latest result of a saved question.
visual: A table-like frame showing rows that come from a stored query.
emotion: The convenience of a saved question you can ask again.
meaning: A view is a saved query that behaves like a read-only table and is recalculated whenever you read from it.
code: create view open_todos with (security_invoker = true) as¶select id, title, user_id¶from todos¶where done = false;
output: A view called open_todos that lists only the todos that are not done.
explanation: A view stores no data of its own, only the query. By default a Postgres view runs with the permissions of its owner, so it can bypass Row Level Security of the tables it reads from. Setting security_invoker to true, available in recent Postgres versions, makes it run with the caller's permissions so the policies still apply.
simple_explain: A view is a saved query with a name. Read from it like a table, and make it security invoker so your RLS rules are not skipped.
analogy: It is like a window cut into your tables that always shows the latest result of a saved question.
syntax: create view name as select ...;
anatomy: create view = save the query | with (security_invoker = true) = use the caller's rights | as select = the query
example_1: create view open_todos as select * from todos where done = false;
example_2: select * from open_todos;
example_3: create view course_summary as select course_id, count(*) as lessons from lessons group by course_id;
variation: create or replace view ...   // change an existing view¶drop view open_todos;   // remove it
used_with: security_invoker, RLS, joins
related: tables, Row Level Security, joins
alternatives: A materialized view that stores the result
where_used: Reports | Simplifying queries | Exposing a limited set of columns
mini_conversation: A: My view shows rows that RLS should hide. | B: Views run as their owner by default, so turn on security invoker.
misconception: ✗ A view always respects the Row Level Security of its tables → ✓ By default a view runs with its owner's rights and can bypass RLS unless security_invoker is on
confused_with: View vs table: a view stores a query, a table stores data.
avoid: Do not expose a view to the API without checking whether it bypasses RLS.
wrong_code: create view open_todos as select * from todos where done = false;
right_code: create view open_todos with (security_invoker = true) as select * from todos where done = false;
