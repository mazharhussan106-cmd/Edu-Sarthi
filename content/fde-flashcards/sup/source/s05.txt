topic: 05 Row Level Security
level: Intermediate
term: Row Level Security (RLS)
cue: Which Postgres feature lets the database itself decide which rows each user may read or change?
category: Security
frequency: Very high
importance: 5
origin: Browsers talk to the database through an open API, so the rules about who sees what must live in the database, and Postgres provides row-level policies for exactly this.
pro_tip: Turn on RLS for every table in an exposed schema, and write policies before launching.
memory_story: RLS is a guard at each row, checking your badge before letting you see or change it.
visual: A table where each row has a lock that opens only for the matching user.
emotion: The calm of knowing a user cannot read another user's data.
definition: Row Level Security is a Postgres feature in which policies attached to a table decide, for each row, whether the current user may select, insert, update or delete it.
explanation: When RLS is enabled on a table, access through the API is denied by default until you add policies. A policy is a rule such as auth.uid() = user_id. The anon and authenticated roles are subject to it, while the service role bypasses it. This is what makes it safe for the browser to call the database directly with the client key.
simple_explain: RLS puts rules on rows. Turn it on, then write policies like each user can see only their own rows, and the database enforces them for every request.
analogy: It is like a guard at each row who checks your badge before letting you see or change it.
formula_rule: Enable RLS → no access → add policies → access only where a policy allows
example_1: A todos table where users see only rows with their own user_id.
example_2: A public blog table where everyone can read but only authors can write.
example_3: A private messages table visible only to sender and receiver.
related: policies, auth.uid(), anon vs service role key, Supabase Auth
word_family: RLS, policy, role, USING, WITH CHECK
where_used: Every table exposed to the API | Multi-user apps | Data privacy
mini_conversation: A: Can users read each other's tasks through the API? | B: Not if RLS is on with a policy that matches each user's own rows.
misconception: ✗ The client key is enough to protect data without RLS → ✓ The client key is public, so RLS is what actually keeps data safe
contrast: RLS vs app-level checks: RLS is enforced by the database for every request, app checks can be bypassed.
avoid: Do not expose a table to the API with RLS turned off.
memory_trick: RLS guards every single row for you.
real_project: Making each learner's progress rows visible only to that learner.
real_interview: An interviewer may ask: Why is RLS important in Supabase?
real_daily: It is like a guard checking your badge at every row.
mcq_question: What happens to API access on a table with RLS enabled but no policies?
mcq_options: A) Everyone can read B) The table is deleted C) Access is denied D) Only admins can read
mcq_answer: C
mcq_why: With RLS on, access is denied until a policy allows it.
fill_blank: RLS rules are written as ____ on a table → policies
apply: How do you let users see only their own rows? → Enable RLS and add a policy comparing auth.uid() with the row's user id

term: Policies (USING and WITH CHECK)
cue: Which two clauses of a policy decide which existing rows a user may see, and which new values they may write?
kind: SQL statement
frequency: Very high
importance: 5
origin: Reading and writing need different checks, so policies have a clause for choosing visible rows and another for validating new or changed rows.
pro_tip: Wrap auth.uid() as (select auth.uid()) in policies so Postgres can cache it and run faster.
memory_story: USING decides what you may look at, and WITH CHECK decides what you may put in.
visual: One filter on existing rows and another gate on rows being written.
emotion: The satisfaction of a rule that stops a cheat before it lands.
meaning: USING filters which existing rows a policy applies to, and WITH CHECK validates the values of rows being inserted or updated.
code: create policy "Users read own todos" on todos¶  for select to authenticated¶  using ((select auth.uid()) = user_id);¶create policy "Users insert own todos" on todos¶  for insert to authenticated¶  with check ((select auth.uid()) = user_id);
output: Logged-in users can read only their own rows and can only insert rows whose user_id is their own.
explanation: Select and delete use USING because they act on existing rows. Insert uses WITH CHECK because it validates new rows. Update can use both: USING picks the rows you may edit, and WITH CHECK validates what the row becomes. You can write separate policies per operation, or one policy for all.
simple_explain: Use USING to say which rows are visible or editable. Use WITH CHECK to say what a new or changed row is allowed to look like.
analogy: USING decides what you may look at, and WITH CHECK decides what you may put in.
syntax: create policy name on table for operation to role using (condition) with check (condition);
anatomy: for = which operation | to = which role | using = existing rows | with check = new values
example_1: using ((select auth.uid()) = user_id)
example_2: with check ((select auth.uid()) = user_id)
example_3: create policy "Public read" on posts for select using (true);
variation: for all using (...) with check (...)   // one policy for every operation¶to anon, authenticated   // apply to both roles
used_with: auth.uid(), enable row level security, roles
related: Row Level Security, auth.uid(), enabling RLS
alternatives: Database functions that check access
where_used: Every multi-user table | Public read tables | Private data
mini_conversation: A: Users can insert rows for other users. | B: Add a WITH CHECK clause that matches user_id to the logged-in user.
misconception: ✗ USING alone protects inserts → ✓ Inserts are validated by WITH CHECK, so an insert policy needs that clause
confused_with: USING vs WITH CHECK: USING filters existing rows, WITH CHECK validates written values.
avoid: Do not write an insert policy without WITH CHECK.
wrong_code: create policy "insert own" on todos for insert using (auth.uid() = user_id);
right_code: create policy "insert own" on todos for insert to authenticated with check ((select auth.uid()) = user_id);
memory_trick: USING looks, WITH CHECK writes.
real_project: Allowing learners to insert and read only their own progress rows.
real_interview: An interviewer may ask: What is the difference between USING and WITH CHECK?
real_daily: It is like what you may look at and what you may put in.
mcq_question: Which clause validates new rows on insert?
mcq_options: A) LIMIT B) USING C) ORDER BY D) WITH CHECK
mcq_answer: D
mcq_why: WITH CHECK validates the values being written.
fill_blank: A select policy uses the ____ clause → using
hindi_to_task: Write a select policy that lets users read only rows where user_id equals their id.
task_answer: create policy "read own" on todos for select to authenticated using ((select auth.uid()) = user_id);

practice_answer: USING

In the SQL Editor you are usually a powerful role, so auth.uid() may be null there.
simple_explain: Policies use auth.uid() to compare the row's owner with the person making the request. Logged-out users give null, so they match nothing.
