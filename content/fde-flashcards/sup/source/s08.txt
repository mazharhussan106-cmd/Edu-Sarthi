term: Connection pooling (transaction vs session mode)
cue: Why do serverless apps connect to Supabase through a pooler, and how do the transaction and session modes differ?
category: Production concept
frequency: High
importance: 5
origin: Each Postgres connection is expensive and the number is limited, so a pooler sits in front of the database and shares a small set of real connections among many clients.
pro_tip: Use transaction mode for serverless and short-lived connections, and a direct or session connection for migrations and long-lived sessions.
memory_story: A pooler is a receptionist who shares a few phone lines among many callers.
visual: Many app connections funnelling into a few database connections.
emotion: The relief of an app that does not crash under too many connections.
definition: Connection pooling reuses a small number of database connections for many clients, and in transaction mode a connection is held only for the length of one transaction, while session mode holds it for a whole client session.
explanation: Supabase provides a pooler, so apps do not open too many direct connections. Transaction mode, commonly on port 6543, suits serverless functions because connections are returned after each transaction, but it does not support some session features such as prepared statements. Session mode, commonly on port 5432 through the pooler, keeps one connection per client and has a limit on clients. The direct connection goes straight to the database, and depends on IPv6 unless you add IPv4 support, so copy the exact strings from your dashboard.
simple_explain: Do not let every serverless function open its own database connection. Connect through the pooler in transaction mode, and use the direct or session string only for tasks like migrations.
analogy: A pooler is a receptionist who shares a few phone lines among many callers.
formula_rule: Serverless app → pooler (transaction mode) → database. Migrations → direct or session connection.
example_1: A Next.js app on serverless hosting using the transaction pooler string.
example_2: A migration command using the direct connection string.
example_3: Too many connections errors disappearing after switching to the pooler.
related: Prisma and Supabase, connection strings, serverless, migrations
word_family: pooler, transaction mode, session mode, direct connection, port
where_used: Serverless hosting | ORMs such as Prisma | High-traffic apps
mini_conversation: A: Our app runs out of connections on serverless. | B: Switch to the transaction pooler connection string.
misconception: ✗ Every app should connect directly to the database for the best speed → ✓ Serverless and high-traffic apps should use the pooler to avoid exhausting connections
contrast: Transaction vs session mode: transaction mode shares connections per transaction, session mode holds one per client session.
avoid: Do not run migrations through the transaction pooler.
